# 3D

A software rasteriser, fixed point, no floats. It exists to draw **UI-sized 3D**: a rotating product, a gauge model, a cover-flow carousel, a loading cube. It is not a game engine, and the limits below are what keep it small.

## Coordinate system

Left handed: **+x right, +y up, +z away from the viewer.** The default camera sits at `z = -4` looking along `+z`. Angles are 16 bit "binary angles" (`65536` = a full turn, `ECCLES_GUI_DEG(d)` converts degrees). World units are Q12 (`ECCLES_GUI_ONE` = 4096 = 1.0, `ECCLES_GUI_FIX(1.5)` for constants).

Object rotation order is roll (z), then pitch (x), then yaw (y). The camera turns by `cam_yaw`, `cam_pitch`.

## Scenes

```c
eccles_gui_obj_t v = eccles_gui_view3d_create(&gui, parent);      // a widget; up to ECCLES_GUI_MAX_VIEWS3D alive
eccles_gui_view3d_t *scene = eccles_gui_view3d_get(&gui, v);      // edit the struct directly...
scene->cam_z = -6 * ECCLES_GUI_ONE;  scene->focal = 300;          // focal length in pixels: bigger = narrower view
int i = eccles_gui_view3d_add(&gui, v, &eccles_gui_mesh_torus, color);
eccles_gui_view3d_set_transform(&gui, v, i, x, y, z, yaw, pitch, roll, scale);   // ...or use the setters, which also redraw
eccles_gui_view3d_changed(&gui, v);      // after editing through the pointer
```

Or draw a scene anywhere, from your own draw callback, with no widget: `eccles_gui_view3d_defaults(&scene, view_h)` then `eccles_gui_draw_view3d(dc, &scene, x, y, w, h)`.

A scene holds `ECCLES_GUI_3D_MAX_OBJECTS` objects. Each has a mesh, a position, rotation, uniform scale (Q12), a color, a mode and flags (`VISIBLE`, `DOUBLE_SIDED`).

## Modes

| Mode | |
|---|---|
| `ECCLES_GUI_3D_FLAT` | one light value per face (default) |
| `_SMOOTH` | light interpolated across the face (Gouraud). needs `vnormals`, else flat. Looks right on round meshes (sphere, torus, cylinder) |
| `_UNLIT` | the plain color |
| `_WIRE` | edges, anti aliased lines, back faces culled |
| `_TEXTURED` | an RGB565 texture (width and height powers of two, up to 256) times the light; needs `uv` on the mesh |

One directional light (`light`, `ambient`) lit in model space per face/vertex (a face costs 3 multiplies). Meshes with `colors` per face override the object color.

## Meshes

Meshes are `const` data in flash and are never copied:

```c
typedef struct {
    const int16_t  *verts;     // x,y,z per vertex, Q12: 4096 = 1.0. keep them within about +-2.0
    const uint16_t *faces;     // 3 vertex indices per face
    const int8_t   *normals;   // optional: 3 per face, unit * 127. NULL = computed at run time (slower)
    const int8_t   *vnormals;  // optional: 3 per vertex, for smooth shading
    const uint16_t *colors;    // optional: one rgb565 per face
    const uint8_t  *uv;        // optional: 2 per vertex (0..255)
    uint16_t nverts, nfaces;
} eccles_gui_mesh_t;
```

**Winding rule: `cross(b - a, c - a)` of a face's three vertices (as raw numbers) points out of the model**, i.e. along the stored normal. Faces wound the other way are culled as back faces (set `DOUBLE_SIDED` for thin things like the `card`). `tools/obj2mesh.py` produces this for you; the built in meshes are checked against the rule by the test suite.

Contract: `largest vertex x scale` must stay below 8.0 (it keeps the 32-bit math from overflowing).

Built in: `cube`, `pyramid`, `cylinder` (16 sides), `sphere` (42 v / 80 f), `torus`, `card` (a 4x4 grid quad for textures). All within a cube of side 2.

## How it renders (and why it is cheap)

1. **Once per frame** (the first band that touches the scene): every vertex goes through one 3x3 matrix and a perspective divide; each face is culled (back face by screen space winding, near plane, off screen), lit and put on a list. With no z buffer the list is sorted far to near (shell sort).
2. **Once per band**: every face on the list whose bounding box touches this band is rasterised into it: edges evaluated with one canonical integer formula (no cracks between neighbours, no double drawn pixels), attributes (light, depth, uv) interpolated from one gradient per triangle.

The projected cache is shared by all bands, so the cost of the maths does not grow with the number of bands.

## Z buffer or painter's algorithm?

- **Without `desc.zbuf`**: faces are sorted by the sum of their vertices' depth. Always right for one convex object (cube, sphere, pyramid, cylinder) and for objects that do not overlap in depth. It can be wrong for concave meshes (the torus can show a wrong overlap at some angles), when objects interpenetrate, or when a surface folds over itself. Use a z buffer for those.
- **With `desc.zbuf`** (same size as the band buffer, 16 bit): per pixel depth test, any scene is right, sorting is skipped. Costs `buf_pixels x 2` bytes more RAM and a compare per pixel.

## Limits

- Faces with a vertex behind the near plane (`near_z`, default 0.1) are **dropped, not clipped**: an object that passes through the camera pops out instead of being cut. Faces whose projected coordinates leave +-8191 pixels are dropped the same way.
- Texture mapping is **affine** (not perspective correct). Subdivide big faces; the built in `card` is 4x4 for this.
- One light, no specular, no shadows, no transparency.
- The per-frame cache holds one scene: two views that share bands re-project for each band.
- Vertices and faces are limited by `ECCLES_GUI_3D_MAX_VERTS / _FACES`; what does not fit is dropped and counted (`faces_dropped`).
- Heavily rotated tall objects: with `ECCLES_GUI_3D_MAX_FACES` below the visible count, the *last* faces in the list are dropped, not the farthest.
